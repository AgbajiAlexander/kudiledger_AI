## 2. Proposed domain and data model

Each organization has its own opaque UUID, display name and status. Each branch is an immutable child of exactly one organization. **A branch ID equals its backing ledger `businesses.id`**. New branches get a new business UUID and a branch mapping in the same transaction. Existing business IDs remain unchanged. Branches cannot be reparented or physically deleted; an archived branch stays in historical reports and may be read by authorized users. Initial design assumes one NGN ledger per branch and no cross-branch customer or debt transfers.

| Record | Keys and constraints |
| --- | --- |
| `organizations` | PK `id`; lifecycle status and timestamps. Ownership is expressed through active OWNER memberships. Require at least one active owner in every owner-change transaction. |
| `branches` | PK `id`, FK to `businesses.id`; immutable `organization_id` FK; unique pair `(organization_id, id)`; status, display metadata and default-branch designation. |
| `organization_memberships` | PK `(organization_id, user_id)`; FKs to organization and existing users; explicit state and role. A user can join multiple organizations independently. |
| `branch_assignments` | PK `(organization_id, branch_id, user_id)`; composite FKs to branch and membership; branch role/state, UTC grant and revocation data. Owners derive all-branch access. Other tenant roles require assignments. |
| `staff_invitations` | Hashed, expiring, single-use tokens binding recipient, organization, grant set and issuer. Accept existing identity after sign-in, or create a new verified identity; no grant before completion. Revalidate issuer, branches and seats on acceptance. |
| `plan_versions`, `plan_entitlements` | Immutable versions define integer branch/seat limits and named feature flags. Plan changes pin a version and are audited. |
| `organization_subscriptions` | Organization-owned, one effective state/version at a time, with UTC effective windows, plan and actor history. Initially provision manually with trial/active/restricted/ended states and no payment gateway. |
| `platform_roles`, `support_grants`, audit tables | Separate platform principals and time-bounded support grants; organization, branch, permitted operations, case, approver and expiry. Append-only state-change records with actor, scope, action, time, outcome and correlation ID. Exclude secrets, raw financial payloads and unrelated customer details. |

Plan limits are enforced server-side inside the same write transaction as branch activation, invitation acceptance or role activation. Count active branches and distinct active organization members, including owners; invitations reserve no seats and can fail cleanly when redeemed after a limit is reached. Feature flags only constrain authorized actions. Recommended downgrade behavior preserves active ledgers, financial reads, recovery and export; block additions while over limit. Proposed restricted/ended policy keeps authorized reads and existing recovery available, blocks new writes after a defined grace period, and needs owner approval before implementation. Emergency suspension and recovery of an existing possibly committed attempt require separately designed controls.

### Financial scope and reporting

- Continue using unique `(business_id, reference)` constraints per transaction kind. One reference may appear in two branches; receipts, write requests and lookups always identify the branch and kind as well as ID or reference. Legacy receipt IDs, labels, UTC timestamps, kobo and reference text remain intact. New receipts may show organization and branch labels; historical-name snapshots would require a separate explicit decision.
- Recovery scope remains `(branch UUID, initiating user UUID, kind)` for the blocking attempt, plus journal ID and ref for verification. Retain existing atomic ownership, prepare/submit/acknowledge protocol and explicit device reminders. No retry on an absent ledger lookup. Recheck scope, role and policy when submitting, including inside the financial transaction. A revocation between prepare and submit stops the write; unresolved records stay audited and can be investigated by an explicitly granted support operator.
- Consolidated reporting is an explicit organization capability. Resolve the eligible branch set using the organization ID and authorized role in the same read snapshot as aggregate queries. Use integer kobo, Lagos day bounds, UTC storage, distinct daily flow versus current debt, reversal rules and overflow tests. Include archived branches unless the owner explicitly filters them. Preview selected branches and distinguish any future limited-branch aggregate from an organization total. Avoid cross-branch customer matching or netting. Cap queries and validate indexes before expanding tenant limits.

## 3. Authorization and active branch

Authorization defaults to deny. Tenant management actions and permission grants require the organization authority described below. Organization-wide analytics permission does not grant access to platform operations.

| Capability | Organization owner | Branch manager | Cashier | Accountant | Restricted support operator |
| --- | --- | --- | --- | --- | --- |
| Manage org, branches, staff and assignments | Own organization; protect last owner | — | — | — | — |
| View subscription; request plan change | Own org; request only | — | — | — | — |
| Create customers; record sales, repayments and expenses | Own org branches | Assigned branches | Assigned branches with explicit confirmation | — | — |
| Read receipts, customers and balances | Own org branches | Assigned branches | Assigned branches, operational fields | Assigned branches | — |
| Adjust debt or reverse a sale | Own org branches, with existing rules and explicit confirmation | — by default | — | — | — |
| Run branch reports; export | Own org branches | Assigned branch reports; export separate | — | Assigned branch reports and scoped export | — |
| Run full organization consolidated reports | Own organization | — | — | — by default | — |
| Recover own attempts | Current branch permission; submit requires financial-write capability | Same | Same | — | — |
| Investigate or resolve other accounts' recovery | Separate support grant | Separate support grant | — | — | Case-, branch-, action- and time-bound. Redacted evidence; reason, confirmation and immutable decision required. No financial edits. |
| Manage subscriptions across organizations | — | — | — | — | — |

A separate platform subscription administrator can manage catalog and organization subscriptions using a distinct administrative API and permissions, protected by MFA and reauthentication for sensitive changes. That role receives no financial, receipt or account impersonation privileges. Support access requires separately approved case scope and cannot be inherited from platform administration. Keep platform authentication/trust separate even if the initial deployment shares FastAPI infrastructure. Verify an existing operator grant can be mapped explicitly and safely; never convert old grants into blanket organization access.

A user selects an organization, then a branch returned by authenticated discovery. The client attaches the selected IDs to every branch URL. A remembered preference is only a hint and must be revalidated. After switching, cancel or ignore late requests and clear forms, receipts, summaries and cached customer choices before loading the new branch. Recovery stays tied to its original branch and account. The API authenticates first, verifies live organization membership and branch ownership/assignment, checks capability and applicable entitlement, then filters every object query by the authorized ledger key. Ignore or reject body-supplied tenant IDs. Use uniform resource errors for foreign identifiers, and test mixed pairs, guessed IDs, bulk/export, receipts and operator routes. Actions that mutate financial records or permissions must read their authorization and write within one transaction so revocation or entitlement checks cannot race the write.

## 4. Migration and compatibility

1. Introduce a version ledger with explicit migration IDs and transactional, rerunnable expansion/backfill. Add organizations, branch mappings and organizations' OWNER memberships beside existing schema. Each legacy business becomes one organization with one default branch. Copy exactly its active legacy owners. Preserve a user's independent membership in several legacy businesses; do not infer common ownership means the ledgers should be joined. Record the business-to-organization mapping once in a uniquely constrained row. Report ownerless or ambiguous records and stop rollout until resolved.
2. Dry-run on an anonymized synthetic legacy fixture and restore a verified backup before rollout. Compare canonical per-table row digests, counts, references, kobo balances, reporting, receipts, recovery stages, account and audit identity, timestamps, triggers and foreign keys. Use an exclusive migration window or quiesced writers with a single migrator. Take a snapshot immediately before changes and verify integrity after applying. Failed migration must roll back without partial mappings. Avoid SQLite DDL operations that implicitly commit; test actual SQLite transactional behavior.
3. Keep legacy endpoints and account setup stable during expansion. Backfill before enabling new reads. Before enabling new writes, ensure every provisioning path creates the legacy business and SaaS mapping atomically under the approved policy. With multi-branch mode enabled, route legacy UI/API requests through the same authorization resolver and pin compatible owner access to the mapped default branch. Staff and additional branches use explicit branch routes only. Do not mirror staff into legacy OWNER memberships. Revoke/retire incompatible sessions or legacy access before exposing staff features. Keep browser reminder key compatibility on the default branch because its business and account IDs are unchanged.
4. Deploy only a compatible application build after SaaS writes begin. Before activation, the old build can operate on untouched legacy tables if expansion is complete and legacy mode is unchanged. After activation, rollback is a forward fix or mode-specific shutdown on the compatible build; an older server could bypass grants or limits. Preserve all committed history. If restore is unavoidable, freeze writes, preserve the current database and reconcile post-snapshot activity and unresolved recovery before authorizing restoration. Full SQLite backups include the metadata. Tenant export and selective restore require their own scoped design. No historical financial row update or reference rewrite is needed in this rollout.

## 6. Decisions for product-owner approval

- **Roles and duties.** Approve who may adjust, reverse, export or view consolidated reports, and the separate support grant policy. Decide whether branch managers need any staff delegation or cashier actions need finer limits.
- **Plans and lifecycle.** Approve seat and branch definitions, owner inclusion, trials, grandfathering, grace periods, downgrade behavior, recovery after suspension, and retention/export after cancellation. No gateway or charged subscription is included.
- **Branch ownership and identity.** Approve one legacy business per organization, immutable branch ownership, branch-local customers and debts, and branch-local reference uniqueness. Any future tenant merge or debt transfer needs an auditable business process and separate design.
- **Platform and operations.** Approve separate admin MFA, time-limited support, audit access and retention, and restore authority. A shared SQLite database increases the blast radius of a bad query, backup or administrative action. Keep current hosting and onboarding gates. Use a measured concurrency and recovery threshold to decide when to validate a PostgreSQL migration separately.
- **Release risks.** Stale assignments or a legacy route can bypass a new policy if route coverage is incomplete. Treat cross-scope leakage, incorrect kobo, duplicate effects, broken recovery, or an unverified rollback as stop conditions. Require negative tests at the API/service boundary and independent review before feature activation.
